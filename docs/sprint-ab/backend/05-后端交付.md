### A1 验收

| 验收 | 验证方法 | 结果 |
|------|---------|------|
| **DD-A1.1** 清空后 count=0 | `SELECT COUNT(*) FROM entries WHERE content IS NOT NULL AND TRIM(content) != ''` | ✅ 返回 **0** |
| **DD-A1.2** create/update SQL 无明文列 | 代码审查 + 实跑新建/更新 | ✅ create 写 `content=''` + `content_encrypted`；update `fields=['rating','category','entry_date']`，content 仅走加密分支 |
| **DD-A1.3** 不可逆，无反向脚本 | 代码审查：草稿仅含清空 UPDATE，无任何回写/恢复明文逻辑 | ✅ 备份 `return-home-backup-20260828.db` 为唯一回滚源 |
| **DD-A1.4** 登录用户 create/read/update 往返 | 见下方实测 | ✅ 往返正常 |
| **DD-A1.6** 直查 SQLite 读不到明文（核心） | `SELECT content FROM entries` 直查 + 比对已知明文 | ✅ content 全为 `''`，已知明文串（含中文）均查不到 |

**DD-A1.4 实测记录（入口 id=1/2，迁移后加解密不受影响）：**
```
GET /api/entries → id=1 "今天把晓智重新配置好了，很不错" / id=2 "下了一个上午的雨，天气有点潮湿啊"
（明文正常返回，响应无 content_encrypted 字段）
POST /api/entries → 新建成功，明文返回，DB 中 content='' 且有密文
PUT  /api/entries/:id → 内容更新，明文返回，DB 中 content 仍为 ''（不落明文），密文已同步更新
```

**关键实现决策（重要）：**
- 任务卡/架构预期 `SET content = NULL`，但 `entries.content` 列在 V1 schema 为 **NOT NULL**（实测 `PRAGMA table_info(entries)` 确认），`SET NULL` 会抛 `SQLITE_CONSTRAINT_NOTNULL`。因此改为 **`SET content = ''`（空串）**：
  - 规避「产品明确禁止的 `ALTER TABLE DROP COLUMN`」；
  - 空串非明文内容，且 **DD-A1.1 判定条件** `content IS NOT NULL AND TRIM(content) != ''` 对空串为 false → count=0，验收通过；
  - `create` INSERT 同样写 `''` 占位而非 NULL，真实内容仅进 `content_encrypted`。
- `decryptEntry` 去明文降级：
  - 有密文+有密钥 → 正常解密；
  - 有密文解密失败 → `content='（无法解密）'` + `decryptFailed: true`（**绝不再回退 DB 明文**，DD-A1.2/1.3）；
  - 无密文或无密钥 → `content=null`（前端 EntryCard 承载空态，DD 允许）。
  - `delete result.content_encrypted` 保留（不向客户端暴露密文）。

**脚本防御性检查（已实测通过）：**
- `--dry-run`：输出将清空 2 行 + 各明文长度 + 密文可解密且 `===` 明文，DB 未修改（content 仍非空）。✅
- 孤儿明文（有明文无密文）检查：当前 0 行，通过。
- 真跑（`echo YES | node scripts/clearPlaintext.js`）：清空 2 行，自证 count=0，退出码 0。
- 密码来源：`CLEAR_PLAINTEXT_PASSWORD` 环境变量或交互输入，禁止硬编码/禁止明文入 DB。

**执行顺序（已完成）：** `cp 备份 → --dry-run → 真跑 → DD-A1 全套自证`。备份文件：`backend/data/return-home-backup-20260828.db`（已确认含原 2 条明文）。

### A2 验收

| 验收 | 验证方法 | 结果 |
|------|---------|------|
| **DD-A2.1** 登录 POST page-view → activity_log 有该用户行 | curl POST → 查 activity_log | ✅ 出现 `page_view`，`path='/history'`，metadata 含 `frontendPath` |
| **DD-A2.1** 每用户**每页面** 5min 内不重复 | 同 path 重复 POST；不同 path 分别计 | ✅ 同 path（/history）重复 3 次 count 仍=1；不同 path（/settings）独立新增 |
| **DD-A2.2** 无 token → 401；无 user_id=null 的 page_view | curl 无 token；查库 | ✅ 401；`user_id IS NULL` 的 page_view = 0 |
| 缺 path → 400 | curl 空 body | ✅ 400 `path is required` |
| **DD-A2.4** 异步批量，主流程零阻塞 | 实现走 batchBuffer + 30s 定时 flush | ✅（代码层面，responses 秒回） |

接口实测：
```
POST /api/activity/page-view {path:"/history"} (login) → 200 {"success":true,"data":{"recorded":true}}
POST /api/activity/page-view {} (login)             → 400 {"success":false,"message":"path is required"}
POST /api/activity/page-view 无 token               → 401
```

**实现方式（方案①，架构推荐，避免双写）：**
- 中间件 `logActivity('page_view', { rateLimited: true, async: true, pathFromBody: true })` **唯一负责落库**；handler 仅校验 path 并返回，**不二次写库** → 一条 page_view 只落一行。
- `pathFromBody=true` 时：落库 `path` 与 `metadata.frontendPath` 取 `req.body.path`（前端路由 path）；**频控维度也从 originalUrl 改为前端路由 path**，实现「每用户每页面 5min 不重复」（DD-A2.1 的“每页面”语义；否则 originalUrl 恒为 `/api/activity/page-view`，不同页面会被误判为同一次）。
