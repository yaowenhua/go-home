## A1 配套：重置密码文案强化（DD-A1.5）

**目标**：管理员重置密码二次确认弹窗，必须红字警告「所有历史日记将永久无法恢复」——当前文案「将不可访问」偏弱，需强化。

**涉及文件**：`frontend/src/views/admin/AdminUserDetail.vue`（`handleResetPassword`）

**关键实现点**：
1. 现文案改为强警告，例如：`重置后该用户的所有历史日记将永久无法恢复（无法读取）。确定继续吗？`
2. 必须以**红字**呈现（可测：CSS 类/样式断言），且是二次确认弹窗（不可一步执行）。
3. **同步核对改密/重置文案区分**：用户本人改密入口（`Settings.vue` 的 `changePassword`，若存在）需区分布局——改密 = 重加密可读（数据保留），重置 = 数据丢失。文案需按产品口径区分：改密提示「修改密码后历史日记将重新加密，可正常读取；但若丢失新密码，历史日记将无法恢复」。若 `Settings.vue` 无改密 UI，跳过此项并在交付说明注明。

**验收标准（可测）**：
- [ ] `AdminUserDetail.handleResetPassword` 确认弹窗文案含**「永久无法恢复」**字样，且为红色警告样式（CSS 断言或截图）。
- [ ] 仍为二次确认（需显式确认才执行重置，取消不执行）。
- [ ] 用户改密入口（若存在）文案为「重加密可读 / 丢失新密码才不可恢复」，与重置严格区分。

## A2：路由切换登录态 page_view 埋点（DD-A2）

**目标**：路由切换（`router.afterEach`）时，**仅登录用户**上报 `page_view`；匿名不发（不污染 DAU）。上报失败零影响。

**涉及文件**：`frontend/src/router/index.js`（新增 `router.afterEach`）、`frontend/src/api/activity.js`（新增封装，可选）

**后端接口契约**：`POST /api/activity/page-view`，Auth Bearer token，Body `{ "path": "<路由全路径>" }`；200 `{ success, data: { recorded } }`；缺 path → 400。

**关键实现点**（架构方案 §5 A2）：
1. `router.afterEach((to) => { ... })` 内：
   - 守卫内取 `useAuthStore().isLoggedIn`，**为真才上报**（匿名不发，DD-A2.2）。
   - 用 `apiClient` 或新封装 `POST /api/activity/page-view { path: to.fullPath }`。
   - **失败零影响**（DD-A2.4）：`.catch(() => {})` 吞掉错误，不阻塞渲染/读写。异步批量入后端缓冲，主流程零感知。
2. **时机**：afterEach 天然只在路由变化时触发（非整页刷新），无需防重复。首屏刷新不触发导航、不额外补一次——**本期不强制首屏上报**，口径只要求「路由切换时」。
3. `initialize()` 已在 beforeEach await 完成，afterEach 里拿到的 `isLoggedIn` 是准确的（store 已初始化）。

**验收标准（可测）**：
- [ ] 登录用户切换页面（如 / → /history）→ network 中出现 `POST /api/activity/page-view`，体含当前 `path`（DD-A2.1）。
- [ ] 完全退出登录/匿名浏览页面 → **不产生** page_view 请求（无 401、无日志行，DD-A2.2）。
- [ ] 断网/接口 500 时，页面渲染与日记读写**完全不受影响**（无 toast、无阻塞、无报错，DD-A2.4）。
- [ ] 同一用户同一页面 5min 内重复切换不重复上报成功计数（后端频控兜底；前端只需确认调用存在即满足）。

## B1：AdminUserDetail 接真实活动日志（DD-B1）

**目标**：后台单个用户详情页「最近活动」区，移除 mock，改为 fetch 真实 `activity_log`；**只显示行为元数据，不渲染任何日记明文**。

**涉及文件**：`frontend/src/views/admin/AdminUserDetail.vue`、`frontend/src/api/admin.js`（新增 `getUserActivity`）

**后端接口契约**：`GET /api/admin/users/:id/activity?limit=20`，admin token；200 返回 `{ success, data: { userId, total, limit, items: [{ id, event_type, path, metadata, created_at }] } }`；404 用户不存在；非 admin 403。**响应绝不含 content 明文**。

**关键实现点**（架构方案 §5 B1）：
1. **api/admin.js 新增**：`getUserActivity(userId)` → GET `/api/admin/users/:id/activity`（默认 limit 20）。
2. **AdminUserDetail.vue**：
   - 移除 `activities = ref([])` 的恒空 mock 逻辑（注释「mock for now」）。
   - `fetchUserDetail` 后**并行** `adminApi.getUserActivity(userId).then(...)` → `activities.value = 映射后数组`。
   - **行为文案映射表**（DD-B1.2）：
     | event_type | 文案 | icon |
     |-----------|------|------|
     | login | 登录 | 🔑 |
     | register | 注册 | 📝 |
     | entry_create | 写日记 | ✍️ |
     | entry_update | 更新日记 | 🔄 |
     | entry_delete | 删除日记 | 🗑️ |
     | page_view | 浏览页面 | 👀 |
     | api_call | 接口访问 | ⚙️ |
     | change_password | 修改密码 | 🔒 |
     | 其他 | 行为记录 | 📌 |
   - `activities` 映射为 `{ type, text, time, icon }`（`text`=映射文案，`time`=`created_at`，`icon`=上表 emoji），模板按此结构渲染。
   - **明文安全**：只展示 `event_type / path / metadata / created_at` 映射出的行为元数据；**不渲染任何日记 content 明文**（后端已保证不返回，前端也不应依赖；page_view 可显示 path 但不渲染日记正文）。
   - **空态**：模板已有 `activities.length === 0` →「暂无活动记录」，**保留**（DD-B1.4）。
   - **独立 loaded state**：`activitiesLoading`/`activitiesLoaded` 与用户加载分离，避免 activities 慢导致整页 loading（架构明确要求）。

**验收标准（可测）**：
- [ ] 后台某用户详情页「最近活动」显示**真实** `activity_log` 数据（登录/写日记/浏览页面等行为 + 时间），非静态 mock（DD-B1.2）。
- [ ] 页面网络请求出现 `GET /api/admin/users/:id/activity`，200 且 data.items 正确映射渲染。
- [ ] 界面**不渲染任何日记 content 明文**——渲染数据仅含行为类型、时间、（可选的 path）元数据，无内容正文（DD-B1.3）。
- [ ] 无活动用户显示「暂无活动记录」，不报错（DD-B1.4）。
- [ ] 非 admin 账号打开该页 → 接口 403，页面不崩（有错误兜底）。
- [ ] activities 加载慢时，用户详情主体不整体 loading（独立 spin）。
