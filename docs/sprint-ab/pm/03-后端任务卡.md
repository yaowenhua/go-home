## A1. 内容加密达标（M2）—— 明文从 DB 彻底退出

**目标**：`entries.content` 明文从 DB 彻底消失，任何路径（含直查 SQLite）都读不到日记明文。安全承诺达标。

**关键现状（已核验）**：DB 现仅 **2 条明文行（id=1/2），且均已有有效 `content_encrypted`**（168/174 字符）。即无「有明文但无密文」的孤儿行，迁移 = 纯清空，零风险零依赖用户密码。但脚本必须做成**防御性**（若未来出现孤儿明文则拒绝）。

### 子任务 A1.1：新增 `backend/scripts/clearPlaintext.js`（一次性迁移脚本）

**涉及文件**：`backend/scripts/clearPlaintext.js`（新增）

**关键实现点**（架构方案 §2）：
1. **执行前强制约束**：文档强约束/脚本引导执行 `cp backend/data/return-home.db backend/data/return-home-backup-$(date +%Y%m%d).db`（一次性不可逆，备份是唯一回滚源）。
2. **防御性检查（不满足即 abort，退出码非 0，绝不丢数据）**：
   - 检查孤儿明文：`SELECT COUNT(*) FROM entries WHERE content IS NOT NULL AND TRIM(content) != '' AND (content_encrypted IS NULL OR content_encrypted = '')` 必须为 **0**，否则 abort。
   - 密文有效性：对「有明文」行逐一用该用户密钥解密 `content_encrypted`，须解出且 `=== content`，否则 abort。取密钥方式 = 与登录一致（`users.content_salt` + 用户当前密码），**交互输入或环境变量取，禁止硬编码、禁止明文密码入库**。
3. **主语句**：`UPDATE entries SET content = NULL WHERE content IS NOT NULL AND TRIM(content) != ''`。
   - 必须用 `SET content = NULL`，**禁止 `ALTER TABLE DROP COLUMN`**（SQLite 兼容性，产品口径明确禁令）。
4. **dry-run 模式**：`node backend/scripts/clearPlaintext.js --dry-run` 只打印「将清空 N 行 + 各明文字符数 + 密文可解密校验结果」，**不写库**。必须先在 dry-run 通过再真跑。
5. **不自证回写**：脚本内无任何回写明文/恢复明文的逻辑（DD-A1.3 由「数据已删除」保证，不提供反向脚本）。

**验收标准（可测）**：
- [ ] `--dry-run` 输出将清空行数与密文校验结果，DB 数据不变（`content` 仍非空）。
- [ ] 真跑后 `SELECT COUNT(*) FROM entries WHERE content IS NOT NULL AND TRIM(content) != ''` 返回 **0**（DD-A1.1）。
- [ ] 直查 SQLite `content` 列读不到任何明文（DD-A1.6，核心判定）。
- [ ] 脚本无回写明文/恢复明文逻辑；`content` 列保留（NULL）但永不再写入（DD-A1.3）。
- [ ] 存在「有明文无密文」行时脚本 abort 且退出码非 0（防御性）。

### 子任务 A1.2：entryController 停止写明文 + 去明文降级

**涉及文件**：`backend/controllers/entryController.js`

**关键实现点**（架构方案 §4 A1.2-6）：
1. **create**：INSERT 去掉 `content` 列 → `INSERT INTO entries (id, user_id, content_encrypted, rating, category, entry_date, created_at)`。`content` 仍从 body 读作加密输入，但**不再入库明文**。对应的 `backend/routes/entries.js` 里 create/update 若显式列出 content 列需一并移除（架构标注「随 controller 内改」）。
2. **update**：`fields` 数组移除 `'content'`（剩 `['rating','category','entry_date']`）。`content` 更新仅走 `content_encrypted = encrypt(...)` 分支（现有 `req.body.content !== undefined` 逻辑保留，去掉 content 进 `updates` 即可，保持 `content_encrypted` 同步更新）。
3. **decryptEntry 去明文降级**：现在解密失败时 `result.content` 回退保留 DB 明文——清空后 content 恒 NULL，回退已无意义且违反「明文从响应退出」。改为：抛错（errorHandler 兜底）**或** `result.content = '（无法解密）'` 占位 + 传 `decryptFailed: true` 标志（前端 EntryCard 显示「内容解密失败（可能为密码变更后旧数据）」）。**禁止**回退 DB 明文。
4. **`delete result.content_encrypted` 保留**（不向客户端暴露密文）。
5. **decryptEntries 空值安全**：`content_encrypted` 为 NULL/空行 → `decrypt` 返回 null → `result.content = null`。前端 EntryCard 需对 null content 承载（不崩、显示占位）——此项需与界面匠确认 EntryCard 现状。

> ⚠️ **前后端协同**：A1.2 的 decrypt 语义改动（回退明文→报错/占位）必须与前端（界面匠）同批落地，避免灰度期内 EntryCard 渲染 NULL 崩。

**验收标准（可测）**：
- [ ] 代码审查 create/update 的 SQL INSERT/UPDATE **无 `content` 明文列**（DD-A1.2）。
- [ ] 登录用户 create/read/update 自己的日记，明文在 API 响应中正常往返（DD-A1.4，加解密不受影响）。
- [ ] 接口响应 JSON 中**无 `content` 明文、无 `content_encrypted` 密文**字段。
- [ ] 解密失败场景：返回占位文案或 `decryptFailed: true`，**不返回 DB 明文**。
- [ ] `content_encrypted` 为 NULL 的行，响应 `content: null` 且不崩。

## A2. 访问统计完整（M3）—— 新增入站端点

**目标**：前端路由切换上报 `page_view`，使 DAU/WAU/MAU 涵盖「登录但不写日记」的用户。后端统计口径无需改动（`activityLogger` 已完整）。**本卡只做后端端点**，前端埋点在【前端任务卡】。

### 子任务 A2.1：新增 `backend/routes/activity.js` + 挂载

**涉及文件**：`backend/routes/activity.js`（新增）、`backend/server.js`（挂载）

**关键实现点**（架构方案 §4 A2，参考实现）：
```js
const router = require('express').Router()
const { authenticate } = require('../middleware/authMiddleware')
const { logActivity } = require('../middleware/activityLogger')
router.use(authenticate)
router.post('/page-view',
  logActivity('page_view', { rateLimited: true, async: true, metadata: { path: ??? } }),
  (req, res, next) => {
    if (!req.body?.path) return res.status(400).json({ success: false, message: 'path is required' })
    res.json({ success: true, data: { recorded: true } })
  })
module.exports = router
```
- **Auth**：`authenticate`，无 token → 401（匿名天然进不来，满足 DD-A2.2）。
- **Body**：`{ "path": "/history" }`（前端路由 path，必填；缺 path → 400）。
- **频控**：复用 `logActivity` 中间件 5min 频控（频控 key = `${eventType}:${userId}:${req.originalUrl}`，同一用户 5min 只记一次）+ 30s 异步批量。
- **⚠️ 记录前端 path 的处理（二选一，选一实现，避免双写）**：
  - 方案①（架构推荐）：给 `activityLogger` 中间件选项加 `pathFromBody` 布尔，为 page_view 开启时 metadata.path + 落库 path 取 `req.body.path`。
  - 方案②：中间件记 originalUrl，handler 内再 `syncRecordEvent`——**此方案必须去掉中间件的落库，否则一条 page_view 落两行**。
  - **明确禁止双写**：middleware 与 handler 二选一。
- **server.js**：`const activityRoutes = require('./routes/activity')` + `app.use('/api/activity', activityRoutes)`（放在 entries 之前、无需 auth 的在后）。

**接口契约**：
| 项 | 值 |
|----|----|
| Method+Path | `POST /api/activity/page-view` |
| Auth | `authenticate`（登录才计；无 token → 401） |
| Body | `{ "path": "/history" }`（必填） |
| 频控 | `logActivity('page_view', { rateLimited: true, async: true })` |
| Response 200 | `{ "success": true, "data": { "recorded": true } }` |
| Response 400 | `{ "success": false, "message": "path is required" }` |

**验收标准（可测）**：
- [ ] 登录用户 `curl -X POST localhost:3001/api/activity/page-view -H 'Authorization: Bearer <token>' -d '{"path":"/history"}'` → 200，`activity_log` 出现该用户 page_view 行（DD-A2.1）。
- [ ] 同一用户同一 path 5min 内重复 POST 不产生重复行（频控生效）。
- [ ] 无 token POST → 401；`activity_log` 无 user_id 为 null 的 page_view 行（DD-A2.2）。
- [ ] 缺 path → 400 `path is required`。
- [ ] `page_view` 走异步批量，主流程零阻塞（DD-A2.4，前端侧验证）。

## B1. 新增按用户查活动日志接口

**目标**：后台单个用户详情页展示该用户**真实**行为记录（登录/写日记/访问等）。只展示行为元数据，**绝不返回日记明文**。

### 子任务 B1.1：adminController.getUserActivity + 路由

**涉及文件**：`backend/controllers/adminController.js`（新增方法）、`backend/routes/admin.js`（新增路由）

**关键实现点**（架构方案 §4 B1）：
1. **getUserActivity(req, res, next)**：
   - 先校验 `:id` 用户存在，不存在 → 404 `{ "success": false, "message": "用户不存在" }`。
   - `SELECT id, event_type, path, metadata, created_at FROM activity_log WHERE user_id = ? ORDER BY id DESC LIMIT ?`（limit 默认 20，上限 100）。
   - **metadata 是 JSON 字符串** → 返回前 `JSON.parse` 成对象，**容错**：解析失败给 `{}`（前端不崩）。
   - **响应白名单只含** `id / event_type / path / metadata / created_at`，**绝不包含任何 entries content / content_encrypted 字段**（DD-B1.3，只读 activity_log 表天然满足）。
2. **路由**：`routes/admin.js` 新增 `router.get('/users/:id/activity', adminController.getUserActivity)`。
   - **路由顺序**：放 `/users/:id` 之后、与 `reset-password`/`status` 同区（紧跟 getUser 最清晰），避免 `:id` 单段路由歧义。
   - **权限继承**：`routes/admin.js` 已统一 `router.use(authenticate, requireAdmin)`，B1 的 admin 校验自动继承，非 admin → 403（DD-B1.5）。**无需重复写**，但需确认 requireAdmin 已挂在本路由所在 router 上。

**接口契约**：
| 项 | 值 |
|----|----|
| Method+Path | `GET /api/admin/users/:id/activity` |
| Auth | `authenticate` + `requireAdmin`（路由层统一）→ 非 admin 403 |
| Query | `limit`（默认 20，max 100） |
| Response 200 | 见下结构 |
| Response 404 | `{ "success": false, "message": "用户不存在" }` |
| Response 403 | `{ "success": false, "message": "..." }`（非 admin） |

```json
{
  "success": true,
  "data": {
    "userId": "xn_ABC",
    "total": 3,
    "limit": 20,
    "items": [
      { "id": 42, "event_type": "entry_create", "path": "/api/entries", "metadata": { "method": "POST", "path": "/api/entries", "statusCode": 201 }, "created_at": "2026-08-28T12:00:00.000Z" },
      { "id": 41, "event_type": "login", "path": null, "metadata": {}, "created_at": "..." },
      { "id": 40, "event_type": "page_view", "path": "/history", "metadata": {}, "created_at": "..." }
    ]
  }
}
```

- **分页**：本期只做 `ORDER BY id DESC LIMIT n`（默认 20），前端一页展示，不做「加载更多」；`total` 返回该用户总日志数便于展示。游标分页（`before_id`）预留列不做（DD-B1.5「N 条即可」）。
- **本期不做**：行为筛选器、行为导出、管理员操作审计。

**验收标准（可测）**：
- [ ] `GET /api/admin/users/:id/activity?limit=20`（admin token）→ 200，返回该用户 `activity_log` 倒序真实列表（DD-B1.1）。
- [ ] 用户不存在 → 404（DD-B1.x）。
- [ ] 非 admin token 访问 → 403（DD-B1.5）。
- [ ] 响应 JSON **无任何 content 明文字段**（DD-B1.3，核心判定，可与 qa 一起直查断言）。
- [ ] metadata 为非法 JSON 时返回 `{}`，不崩。
- [ ] `limit` 默认 20、上限 100，超限被截断。
