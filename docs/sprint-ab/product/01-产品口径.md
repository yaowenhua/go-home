## 1. Sprint A 产品口径

### A1. 内容加密达标（M2）—— 明文从 DB 彻底退出

**目标陈述**：「管理员读不到明文」是 V2 内容加密的核心承诺。达标 = 明文从 DB 彻底消失，任何路径（含直查 SQLite）都无法读到日记明文。

#### 产品决策点 ① 拍板：接受「改密/重置后旧历史不可恢复」的取舍

- **决策**：**接受**。清空 `entries.content` 明文，只保留 `content_encrypted`。明文从 DB 彻底退出。
- **理由**：
  - 需求 2.4.2 F4.5 与 PRD「关键设计决策」已明确推荐「删除 content，仅保留 content_encrypted」；方案 A（密码派生密钥）的已知代价正是「密码重置导致数据不可读」。这是**安全承诺的必然代价**，不是缺陷。
  - 「保留 content 做降级」当前只带来一个表面好处（改密/重置后老数据能读），但它**直接击穿**「管理员读不到明文」这一核心承诺。二选一，安全承诺优先级更高——这是产品的原初卖点，不可妥协。
  - 加密体系尚未大面积铺开（DB 现仅 2 条明文日记），**迁移代价为零**。现在不彻底清理，数据越多越难回头。宜早不宜迟。
- **用户侧提示（必须落地）**：
  - **管理员重置密码**：二次确认弹窗必含红字警告「重置后该用户的**所有历史日记将永久无法恢复**」。可复用现有 `AlertUserDetail` 的 confirm 文案，但必须补上「永久无法恢复」这一句（当前文案「将不可访问」偏弱，需强化为「永久无法恢复/读取」）。
  - **用户本人改密**（若有此入口）：同样弹提示「修改密码后历史日记将重新加密，可正常读取；但若丢失新密码，历史日记将无法恢复」。改密是重加密（数据可保留），与重置（数据丢失）性质不同，文案需区分。

#### A1 验收标准（Done Definition，可测）

- [ ] **DD-A1.1**：`entries` 表中所有行的 `content` 字段均为 `NULL` 或空字符串——`SELECT COUNT(*) FROM entries WHERE content IS NOT NULL AND TRIM(content) != ''` 返回 **0**。
- [ ] **DD-A1.2**：`entryController.js` 的创建/更新路径**不再写入** `content` 明文（SQL INSERT/UPDATE 中不含 content 明文列），仅写 `content_encrypted`。
- [ ] **DD-A1.3**：清空操作不可逆——清空后**无任何 SQL / 脚本 / 回滚路径**能恢复明文（安全承诺由数据已清除保证，而非仅靠权限）。
- [ ] **DD-A1.4**：后端正常读取流程不变——已登录用户创建/读取/更新自己的日记，明文在 API 响应中正常往返（加解密不受影响）。
- [ ] **DD-A1.5**：管理员重置密码弹窗含「所有历史日记将永久无法恢复」警告文案（可测：截图或文案断言）。
- [ ] **DD-A1.6**：安全验证——直查 SQLite（`sqlite3` 打开 DB 选 content 列）**读不到任何日记明文**。此条为本需求的**核心判定**。

### A2. 访问统计完整（M3）—— page_view 补埋点，统计口径完整

**目标陈述**：DAU/WAU/MAU 反映「有过任何活跃行为的登录用户」，而不是只统计「写了日记」的用户。「登录但没写日记」的用户必须被计入活跃。

#### 产品决策点 ② 拍板：page_view 仅登录用户上报，匿名不计入

- **决策**：前端路由切换（`router.afterEach`）仅**在已登录（有有效 token）时**上报 `page_view`；**匿名用户不上报**，不算活跃。
- **理由**：
  - DAU/WAU/MAU 的口径是「不同**用户**数」，统计对象是注册用户。匿名访问没有 `user_id`（中间件里是 `null`），计入会污染活跃口径，让 DAU 虚高且无法归因到具体用户。
  - 后端 `activityLogger` 的频控 key 用的是 `req.user?.userId || 'anonymous'`——匿名会聚成一个「anonymous」桶，统计 `COUNT(DISTINCT user_id)` 时 null 不计入，但会制造垃圾日志行。**前端只对登录态上报**，从源头避免。
  - 路由变化是「打开页面」这一互动的信号，最能覆盖「登录但没动作」的用户。补上它，DAU 口径才与「产品活跃」对齐。
- **实现口径**：前端在 `router.beforeEach/afterEach` 感知登录态；仅当 `authStore.isLoggedIn` 为真时，调用现有上报（走 `/api/...` 里的活动日志接口，复用后端 `page_view` 中间件与 5min 频控），携带当前路由 path。

#### A2 验收标准（Done Definition，可测）

- [ ] **DD-A2.1**：前端在路由切换时对**已登录**用户触发 `page_view` 上报（`POST` 携带当前 path），每用户每页面 5min 内不重复（复用后端频控）。
- [ ] **DD-A2.2**：**匿名/未登录**浏览页面**不产生** `page_view` 日志（`activity_log` 中无 user_id 为 null 的 page_view 行）。
- [ ] **DD-A2.3**：DAU 口径完整——一个「登录后只浏览页面、未写日记」的用户，在当日 DAU 中被计入（构造此场景：登录→切 1 个页面→查 `GET /api/stats/dau`，该用户出现在计数与 breakdown）。
- [ ] **DD-A2.4**：`page_view` 属高频事件，日志对主流程零影响——上报失败（如断网）不影响页面渲染与日记读写。
- [ ] **DD-A2.5**：管理后台 DAU/WAU/MAU 卡片能反映 page_view 带来的活跃（数值随浏览行为上升，可观察）。

## 2. Sprint B 产品口径（2.3 后台管理 M4）

### B1. AdminUserDetail 真实活动日志

**目标陈述**：后台单个用户详情页的「最近活动」区，从 mock 改为展示该用户的**真实**登录 / 写日记 / 访问等行为记录。

#### 产品决策点 ③ 拍板：展示口径与后端 API

- **决策**：
  - 后端新增查询该用户最近 `activity_log` 的接口（如 `GET /api/admin/users/:id/activity?limit=N`，admin 权限），返回倒序「行为类型 + 时间 + 相关元数据（path/entry）」列表。
  - 前端 `AdminUserDetail.vue` 移除 mock，改为 fetch 真实数据。**空态**显示「暂无活动记录」（保留现有文案）。
  - **展示内容**：`login / register / entry_create / entry_update / page_view / api_call` 均可展示；行为标签用用户可读文案映射（如 `登录`、`写日记`、`更新日记`、`浏览页面`），并显示时间。**不含任何日记明文内容**（严禁在后台泄露用户内容；page_view 可显示 path 但不渲染日记正文）。
- **理由**：
  - 这是「后台能看到用户行为」的价值点：管理员要判断某账号是否活跃、是否异常，mock 数据会让运维误判为「系统没记录」。
  - 只展示行为元数据（类型+时间+页面路径），**不展示日记明文**——这既是产品边界（后台"只查行为、不读内容"），也与 A1 的安全承诺一致。后台读取用户内容即使技术上可行，也不符合「管理员不读明文」的定位，需在接口层就切掉。
- **明确不做（本期）**：行为筛选器、行为导出、管理员操作审计（admin 自己的操作日志）——留给后续，本期只把「用户的行为能看到」补真实。

#### B1 验收标准（Done Definition，可测）

- [ ] **DD-B1.1**：后端存在 admin 权限的按用户活动查询接口，返回该用户 `activity_log` 倒序列表（含 event_type、created_at、path/metadata）。
- [ ] **DD-B1.2**：`AdminUserDetail.vue` 的「最近活动」区显示**真实** `activity_log` 数据（非静态 mock），能正确渲染：写日记、登录等行为 + 时间。
- [ ] **DD-B1.3**：接口/前端**不返回、不渲染**任何日记 `content` 明文（可测：接口响应 JSON 中无 content 明文字段）。
- [ ] **DD-B1.4**：空态正确——该用户无活动时显示「暂无活动记录」，不报错。
- [ ] **DD-B1.5**：分页/条数可控——返回最近 N 条（如最近 20 条）即可，避免一次性拉全量；接口权限校验为 admin，非 admin 访问 403。

**优先级**：Sprint A 两件（A1 安全 > A2 统计）→ Sprint B（管理后台真实日志）。A1 是硬安全承诺，优先级最高，属发布阻塞项；A2、B1 属体验与可信度补全，不阻塞发布但应随 Sprint 完成。

**风险提示**：A1 清空明文是**一次性、不可逆**操作。执行前需备份 DB（`cp return-home.db return-home-backup-YYYYMMDD.db`），并仅在确认加密读写正确（DD-A1.4 通过）后执行清空。清空动作由后端脚本执行，禁止手工 `ALTER TABLE DROP COLUMN`（SQLite 兼容性），采取 `UPDATE entries SET content = NULL` 即可达「无明文」判定。
