## 0. 代码现状核验结论（先于设计，决策依据）

设计前直接查了线上 DB（`backend/data/return-home.db`，better-sqlite3）：

| 项 | 实测结果 | 对设计的影响 |
|----|---------|-------------|
| `entries` 明文行 | **2 条**明文（id=1/2），且**两者均已带有效 `content_encrypted`**（168/174 字符加密串） | **A1 迁移不需要逐行派生密钥**——现有明文行的密文早已生成。迁移 = 直接 `UPDATE entries SET content = NULL`，零风险、零依赖用户密码 |
| 无「有明文但无密文」的行 | 查询 `content 非空 AND content_encrypted 为空` 得 **0 行** | 迁移无需「先加密再清空」的 step；无不可恢复的孤儿明文 |
| `users` | 1 个用户（admin），`content_salt` 已存在 | 加解密链路完整，可走缓存密钥 |
| `activity_log` | 已有 `api_call`/`entry_create`/`login` 三类事件；`page_view` 中间件逻辑就位但**前端零埋点** | A2 只补前端埋点 + 开放一个入站端点，后端统计口径无需改动 |
| B1 后端 | **无**按 user_id 查 activity 的接口 | 需新增（DD-B1.1） |
| B1 前端 | `AdminUserDetail.vue` `activities` 为 `ref([])` 恒空 mock，模板已渲染但从不 fetch | 只需接真实接口（DD-B1.2） |

**关键简化**：产品口径文档担心的「每行用户派生密钥才能加密」在**当前数据下不成立**——2 条明文行的密文已存在。迁移被简化为纯清空操作。但脚本仍需做成**防御性**的（见 A1 脚本设计）：若未来出现「有明文无密文」的行，拒绝清空并告警，杜绝数据丢失。

## 2. 数据迁移脚本设计（A1，一次性不可逆）

**文件**：`backend/scripts/clearPlaintext.js`（node 运行，非手工 SQL）

### 语义
`entries.content` 明文从 DB 彻底退出，只保留 `content_encrypted`。清空后无任何 SQL/回滚路径能恢复明文（安全由数据已删除保证，DD-A1.3）。

### 执行前必做（脚本内强制拦截或文档强约束）
```bash
cp backend/data/return-home.db backend/data/return-home-backup-$(date +%Y%m%d).db
```

### 防御性检查（宁可失败也不丢数据）
脚本需先验证，不满足即中止（退出码非 0）：
1. **0 行「有明文且无密文」**：`SELECT COUNT(*) FROM entries WHERE content IS NOT NULL AND TRIM(content) != '' AND (content_encrypted IS NULL OR content_encrypted = '')` 必须为 **0**，否则 abort——这些行无密文，清空即永久丢数据。
2. **所有「有明文」行的密文有效**：对第 1 步查出的明文行（即 `content 非空` 的行）逐一用该行用户的加密密钥 **解密验证** `content_encrypted` 能解出且 `=== content`（防密文写错）。此步为 dry-run 强校验；生产若已有密文一致（当前 2 行即如此），可通过。
   - 取密钥方式：与登录一致——`users.content_salt` + 该用户当前密码。脚本需要**交互式输入用户密码**或从环境变量取得（**不能**硬编码、不能要求管理员明文密码入库）。
   - **简化路径**：当前 2 行密文已存在且运行时可解密验证；若未来数据同样在写入时密文已正确，此检查通过成本低。

### 执行主语句
```sql
UPDATE entries SET content = NULL WHERE content IS NOT NULL AND TRIM(content) != '';
```
> 用 `SET content = NULL`（非 `DROP COLUMN`），符合产品口径禁令，SQLite 向前兼容。

### Dry-run 模式
`node backend/scripts/clearPlaintext.js --dry-run`：只打印「将清空 N 行 + 各明文字符数 + 密文可解密校验结果」，不写库。**先在 dry-run 过，再真跑。**

### 与改密/重置的交互约束（产品已确认接受）
- 脚本只在**明文迁移**这一时点运行；日常「改密/重置后旧数据不可读」已是既有语义（`adminController.resetPassword` 注释已声明旧密文永久不可读，密钥派生自旧密码，改密后新密钥解不开旧密文）。清空明文后此语义不变，仍成立。

## 3. 接口契约

### A2：上报 page_view
| 项 | 值 |
|----|----|
| Method+Path | `POST /api/activity/page-view` |
| Auth | `authenticate`（登录才计；无 token → 401，前端只在登录态发） |
| Body | `{ "path": "/history" }`（当前路由 path，必填） |
| 频控 | 复用 `logActivity('page_view', { rateLimited: true, async: true })` 中间件的 5min 频控 + 30s 异步批量 |
| Response 200 | `{ "success": true, "data": { "recorded": true } }` |
| Response 400 | `{ "success": false, "message": "path is required" }`（缺 path） |
| 说明 | 匿名拦截：中间件 `req.user` 为 null 时**不落库**（可选加一道 `if (!req.user) return res.status(401)` 更明确；但端点设计为仅 authenticate，天然只有登录用户能到） |

### B1：按用户查活动日志
| 项 | 值 |
|----|----|
| Method+Path | `GET /api/admin/users/:id/activity` |
| Auth | `authenticate` + `requireAdmin`（路由层统一）→ 非 admin 403（DD-B1.5） |
| Query | `limit`（默认 20，max 100，MAU 上限）、`before_id`（可选，游标分页，本期可只做 limit；见分页说明） |
| Response 200 | 见下结构 |
| Response 404 | `{ "success": false, "message": "用户不存在" }` |
| 明文安全 | 响应**绝不包含** entries.content / content_encrypted 任何字段（DD-B1.3）——只读 `activity_log` 表，天然不含日记内容 |

#### Response 200 结构
```json
{
  "success": true,
  "data": {
    "userId": "xn_ABC",
    "total": 3,
    "limit": 20,
    "items": [
      {
        "id": 42,
        "event_type": "entry_create",
        "path": "/api/entries",
        "metadata": { "method": "POST", "path": "/api/entries", "statusCode": 201 },
        "created_at": "2026-08-28T12:00:00.000Z"
      },
      { "id": 41, "event_type": "login", "path": null, "metadata": {}, "created_at": "..." },
      { "id": 40, "event_type": "page_view", "path": "/history", "metadata": {}, "created_at": "..." }
    ]
  }
}
```

#### 分页说明（DD-B1.5）
产品口径要求「返回最近 N 条即可，避免全量」。两个可选实现：
- **方案一（推荐，本期够用）**：`ORDER BY id DESC LIMIT ?`，默认 20。前端一页展示即可，不做「加载更多」。`total` 返回该用户总日志数便于展示。
- **方案二（游标，若后续要滚动）**：`WHERE user_id = ? AND id < ? ORDER BY id DESC LIMIT ?`，用 `id`（自增主键）做游标，加 `before_id`。本期不必，预留列即可。

> 加一条对 `(user_id, id)` 的索引更稳。现有 `idx_activity_log_user_id` 已够 LIMIT 20 场景；若做滚动分页再加 `idx_activity_log_user_date` 族。本期不强制新增索引。

## 4. 后端实现要点（给数据芯）

### A1
1. **clearPlaintext.js**：见第 2 节。核心 = dry-run 校验 + 单条 `UPDATE SET content = NULL`。**执行顺序**：cp 备份 → `--dry-run` → 真跑 → 跑 DD-A1.1/A1.6 验证 SQL。
2. **entryController.create**：INSERT 去掉 `content` 列（`INSERT INTO entries (id, user_id, content_encrypted, rating, category, entry_date, created_at)`）。`content` 保持从 body 读作加密输入，但**不再入库明文**。
3. **entryController.update**：`fields` 数组移除 `'content'`（`['rating','category','entry_date']`）；`content` 更新仅走 `content_encrypted = encrypt(...)` 分支（现有逻辑已按 `req.body.content !== undefined` 单独处理，去掉 content 进 `updates` 即可，保持 `content_encrypted` 同步更新）。
4. **decryptEntry 去明文降级**：现在解密失败时 `result.content` 回退保留 DB 明文——清空后 `content` 恒 NULL，此回退已无意义且违反「明文从响应退出」语义。改为：解密失败 `throw` 或留 `result.content = '（无法解密）'` 占位而非回退原值。**注意**：`delete result.content_encrypted` 保留（不向客户端暴露密文）。
   - 需和后端确认交互：解密失败当前是 `console.warn` + 保留 content。建议改抛错（由 errorHandler 兜底）或返回占位文案——但**不能**返回 DB 里的明文（本就没有了）。可向前端传 `decryptFailed: true` 标志，由 EntryCard 显示「内容解密失败（可能为密码变更后旧数据）」。
5. **decryptEntries 空值安全**：`content_encrypted` 为 NULL/空的行，`decrypt` 返回 null → `result.content = null`，前端 EntryCard 需对 null content 有承载（不崩、显示占位）。确认 EntryCard 现状，必要补空态。
6. **验收自证**：`SELECT COUNT(*) FROM entries WHERE content IS NOT NULL AND TRIM(content) != ''` 应为 0（DD-A1.1）；`sqlite3` 直查 content 读不到明文（DD-A1.6）；登录用户 create/read/update 正常往返（DD-A1.4）。

### A2
1. **routes/activity.js**：
```js
const router = require('express').Router()
const { authenticate } = require('../middleware/authMiddleware')
const { logActivity } = require('../middleware/activityLogger')
router.use(authenticate)
router.post('/page-view',
  logActivity('page_view', { rateLimited: true, async: true }),
  (req, res, next) => {
    if (!req.body?.path) return res.status(400).json({ success: false, message: 'path is required' })
    res.json({ success: true, data: { recorded: true } })
  })
module.exports = router
```
   - 注意 `logActivity` 复用：频控 key = `${eventType}:${userId}:${req.originalUrl}`（originalUrl = `/api/activity/page-view`，同一用户 5min 内只记一次，符合 DD-A2.1）。`path` 通过 middleware 的 metadata 记录（`metadata.path`），落库的 `path` 字段是 originalUrl——**如需记录前端路由 path**（如 `/history`），让 handler 把 `req.body.path` 额外 `syncRecordEvent` 或在 metadata 覆盖。建议：middleware 记 originalUrl 即可满足「活动」，前端实际路由 path 可由 `path` 字段补充——为准确归因，handler 内再 `syncRecordEvent('page_view', { userId, path: req.body.path })` 且同样做 5min 频控（此时中间件的频控可去掉避免双写——**二选一**，推荐：用中间件 + 在 metadata 里带前端 path，见下）。
   - **推荐实现（避免双写）**：直接用 `logActivity('page_view', { rateLimited: true, async: true, metadata: {...} })`，但 metadata 在中间件工厂期是静态。故**最佳**是：`router.post('/page-view', authenticate, handler)`，handler 内手动 `syncRecordEvent('page_view', { userId: req.user.userId, path: req.body.path, ... })` + 复用 activityLogger 的频控/批量逻辑。为避免复制逻辑，可让 handler 复用 `logActivity` 中间件，再在该中间件基于 `req.body` 动态注入 metadata——
   - **简洁定案**：中间件 `logActivity('page_view', { rateLimited: true, async: true })`（记 originalUrl、频控、批量），handler 校验 `path` 后返回。前端路由 path 已可从日志 `metadata.path` 读（originalUrl）。若产品要纯前端 path（`/history`），在 `activityLogger` 里给 page_view 特殊处理太侵入，**本期在 metadata 里存前端 path 更易**：给中间件选项加 `pathFromBody` 布尔，为 page_view 开启时 metadata.path + 落库 path 取 `req.body.path`。见实现备注。

2. **server.js**：`const activityRoutes = require('./routes/activity')` + `app.use('/api/activity', activityRoutes)`（放在 entries 之前、无需 auth 的在后）。

### B1
1. **adminController.getUserActivity(req,res,next)**：
   - 先校验 `:id` 用户存在（404）。
   - `SELECT id, event_type, path, metadata, created_at FROM activity_log WHERE user_id = ? ORDER BY id DESC LIMIT ?`（limit 默认 20，上限 100）。
   - metadata 存的是 JSON 字符串 → 返回前 `JSON.parse` 成对象（容错：解析失败给 `{}`）。

## 6. 风险与回滚点

### A1（最高风险，一次性不可逆）
| 风险 | 缓解 / 回滚 |
|------|------------|
| **清空后明文永久丢失** | 迁移**前必须 `cp` 备份 DB**（`return-home-backup-YYYYMMDD.db`）。备份是**唯一**回滚源；一旦清空且删备份，不可逆（产品的安全承诺正是要「不可恢复」） |
| 数据无密文被误清（孤儿明文） | 脚本防御性检查：存在「有明文无密文」行即 abort（见第 2 节）。当前数据 0 行——通过 |
| 密文与会话密钥不匹配 | dry-run 阶段用各用户密钥解密校验「密文解出 == 明文」；不匹配 abort |
| 迁移时生产在写 | 脚本应在**停服/低峰**执行；SQLite 单写锁下 `UPDATE` 原子完成 |
| decrypt 改行为影响前端 | 解密失败语义从「回退明文」改「报错/占位」——需前后端同步改，避免灰度期内 EntryCard 渲染 NULL 崩 |
| 回滚 | 唯一可靠回滚 = 从备份 `cp` 还原 DB。**不提供**「恢复明文」的反向脚本（会击穿安全承诺，DD-A1.3） |

### A2
| 风险 | 缓解 |
|------|------|
| 埋点拖慢/失败影响页面 | 异步 + `.catch(()=>{})`，批量入后端缓冲；前端零阻塞 |
| 匿名污染 DAU | 前端只在登录态发 + 端点仅 authenticate（DD-A2.2） |
| page_view 频控 key 无前端 path 区分 | 5min/用户/路由级频控，见第 4 节 activity.js 备注 |
